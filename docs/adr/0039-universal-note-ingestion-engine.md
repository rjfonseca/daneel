# ADR 0039: Universal Note Ingestion Engine

* Status: accepted
* Date: 2026-11-09

## Context and Problem Statement

Daneel originally provided note ingestion through a narrow, specialized `daneel ingest` CLI command and an `ingest_meeting_notes` Model Context Protocol (MCP) tool. Both were strictly coupled to Google Meet and Gemini meeting transcript processing, extracting participant lists and action items into `sources/reunioes/`. In parallel, ADR 0030 introduced `CaptureNote`, which permitted creating raw text notes directly in `inbox/` via a local ConnectRPC call.

However, knowledge workers, researchers, and automated AI agents frequently capture notes, documents, and reference materials across diverse external locations:
1. **External Host Filesystem Sources**: Meeting transcripts, project RFCs, or downloaded documentation (e.g. `~/Downloads/architecture-decision.md`, `~/Downloads/research-papers/`) outside the vault root.
2. **Batch Directory Imports**: Collections of markdown files generated by external tools, harvesters, or local scripts requiring recursive ingestion into dedicated vault folders (e.g. `inbox/` or `notes/rfc/`).
3. **Multimodal Interface Inconsistency**:
   - The CLI (`daneel ingest`) failed when passed arbitrary markdown files, interpreting missing meeting headers as errors.
   - The Web Cockpit only supported creating single scratchpad notes through `QuickCaptureDialog`, lacking drag-and-drop file upload or host filesystem path ingestion.
   - The Terminal UI (TUI) lacked any visual file-browsing or ingestion view.
   - MCP tools lacked generic file and directory ingestion capabilities for autonomous coding agents.

### Ingestion Safety, Frontmatter, and Indexing Challenges

Ingesting arbitrary host files into a personal knowledge vault introduces several operational and security hazards:
- **Path Traversal & Symlink Attacks**: Malicious or malformed paths (e.g. `../../etc/passwd` or symlinks pointing outside the vault root) could compromise system security or corrupt files outside the vault boundaries.
- **Silent Overwrites & Data Loss**: Ingesting files with colliding names could clobber existing notes containing valuable historical context.
- **Broken Frontmatter & Metadata Loss**: External notes often possess existing YAML frontmatter, custom metadata, or no frontmatter at all. A naive file copy either loses provenance (ingestion timestamp, source origin) or corrupts existing schemas.
- **Search & Graph Desynchronization**: Adding files directly to disk without immediately updating the SQLite FTS5 search index or notifying the live Web cockpit leaves the galaxy graph desynchronized until a manual reindex or daemon restart.

## Decision Drivers

* **Universal Multi-Surface Parity**: Provide a single, consistent ingestion experience across all user and agent interfaces: CLI (`daneel ingest [paths...]`), TUI (`9: 📥 Ingest`), Web Cockpit (`QuickCaptureDialog` file upload / host path tab), and MCP (`ingest_note`, `ingest_path`).
* **Strict Vault Boundary & Path Safety**: Guarantee rooted containment (`safefile.WriteFile`, path canonicalization, strict prefix enforcement) and disallow escaping symlinks or directory traversals.
* **Non-Destructive Collision Resolution**: Ensure zero data loss by generating deterministic, collision-safe timestamps or incremental suffixes (`filename-YYYYMMDD-HHMMSS.md`) when destination paths conflict.
* **Frontmatter Preservation & Provenance Synthesis**: Intelligently preserve existing YAML frontmatter while synthesizing essential metadata (`title`, `ingested_at`, `source_path`) when missing.
* **Immediate Searchability & Ambient Reactive Updates**: Atomically update the SQLite FTS5 search index and emit live reload events (`ACTION_GALAXY_RELOAD`) across active ConnectRPC web streams.
* **Backwards Compatibility**: Maintain full backward compatibility for existing meeting transcript processing (`daneel ingest --zip`, no-arg inbox scanning) and existing `CaptureNote` RPC workflows.
* **Strict Open-Source Invariants**: Enforce English-only interface strings, zero corporate or personal leaks, and pure open-source personas and paths.

## Considered Options

* **Option 1: Unified Core Ingestion Engine (`internal/ingest`) with Surface Adapters (Chosen)**:
  * Implement a dedicated, reusable core package (`internal/ingest`) that handles filesystem validation, frontmatter parsing, collision resolution, safe file writes, SQLite FTS5 indexing, and live reload event dispatching.
  * Thin adapters connect CLI, ConnectRPC (`GraphService`), MCP tools, Web UI, and TUI to the core engine.
  * *Pros*: Single source of truth for security boundaries and collision semantics; DRY implementation; guaranteed consistent behavior across CLI, Web, TUI, and AI agents.
  * *Cons*: Requires establishing clear API contracts and plumbing event hubs and search engines across entry points.

* **Option 2: Ad-Hoc Surface-Specific Implementations**:
  * Implement file reading, path checks, and writing separately within `cmd/ingest.go`, `internal/mcp/server.go`, `cmd/serve.go`, and `internal/tui/`.
  * *Pros*: Avoids creating a shared package; fast isolated changes.
  * *Cons*: Extreme duplication of path security and collision avoidance logic; high risk of inconsistent frontmatter synthesis, missed FTS5 reindexing, or security regressions across surfaces.

* **Option 3: Daemon-Only Remote Ingestion via ConnectRPC**:
  * Require all ingestion actions across CLI, TUI, and MCP to connect to a running `daneel daemon` via Unix domain socket or HTTP/2 ConnectRPC.
  * *Pros*: Guarantees that only the daemon writes to the vault and SQLite database.
  * *Cons*: Breaks standalone CLI and offline TUI usage when the daemon is not running; forces unnecessary client-server IPC overhead for local CLI operations; poor developer ergonomics in headless or script environments.

## Decision Outcome

Chosen option: **Option 1: Unified Core Ingestion Engine (`internal/ingest`) with Surface Adapters**.

### Detailed Component Specifications

#### 1. Core Ingestion Engine (`internal/ingest`)

The engine provides thread-safe ingestion primitives initialized with the vault root, search engine, and daemon event hub:

```go
type IngestOptions struct {
    Destination string   // Relative vault directory (default: "inbox")
    Recursive   bool     // Recursively traverse directories (default: true)
    Move        bool     // Remove source file after successful ingestion (default: false)
    SourceURL   string   // Optional origin URL or reference
    Tags        []string // Optional tags to append to frontmatter
}

type IngestedNote struct {
    SourcePath string `json:"source_path,omitempty"`
    RelPath    string `json:"rel_path"`
    Title      string `json:"title"`
    SizeBytes  int64  `json:"size_bytes"`
    Warning    string `json:"warning,omitempty"`
}

type IngestReport struct {
    Items          []IngestedNote `json:"items"`
    TotalProcessed int            `json:"total_processed"`
    Errors         []string       `json:"errors,omitempty"`
}

type Engine struct {
    vaultRoot    string
    searchEngine *search.Engine
    eventHub     daemon.Hub
}
```

##### Ingestion Workflow and Invariants
1. **Path Sanitization and Containment**:
   - Destination paths must be relative to the vault root and resolved using `filepath.Clean`.
   - Any path resolving outside `vaultRoot` or traversing symlinks outside the vault root is immediately rejected with an explicit error.
2. **Collision Avoidance**:
   - If the target file (e.g. `inbox/architecture.md`) already exists in the destination, the engine appends a timestamp (`inbox/architecture-20261109-170000.md`) or incremental numeric counter, guaranteeing that no existing file is overwritten.
3. **Frontmatter Synthesis & Metadata Preservation**:
   - If the markdown file contains existing YAML frontmatter:
     - The YAML structure is parsed and preserved.
     - Missing `title` fields are populated from the first Markdown `# Header` or the file basename.
     - `ingested_at` timestamp and optional `source_path` / `source_url` attributes are recorded.
   - If no frontmatter exists:
     - A minimal valid YAML frontmatter header is synthesized with `title`, `ingested_at`, and source references.
4. **Meeting Transcript Auto-Detection**:
   - When a note exhibits Google Meet / Gemini transcript signatures, the engine can route or delegate extraction to `internal/meetings/processor.go`, archiving structured artifacts into `sources/reunioes/`.
5. **Move Semantics (`--move`)**:
   - When `Move: true` is requested, the source file on the host filesystem is deleted **only** after the destination file has been written, flushed to disk, and verified.
6. **Atomic Search Indexing & UI Event Dispatch**:
   - Ingested notes are immediately parsed and inserted into the SQLite FTS5 search index (`searchEngine.IndexNote`).
   - If `eventHub` is present, the engine emits `UIEvent{Action: "ACTION_GALAXY_RELOAD"}` so that connected Web Cockpit sessions dynamically refresh their Sigma.js graph views without requiring a page reload.

#### 2. CLI Extension (`cmd/ingest.go`)

The `daneel ingest` CLI command is generalized to accept any number of file or directory arguments:

```bash
daneel ingest <file-or-dir> [more-paths...] [flags]
```

* **Flags**:
  - `-d, --dest <dir>`: Target vault directory (default: `"inbox"`).
  - `-r, --recursive`: Recursively scan directories (default: `true`).
  - `-m, --move`: Remove source file(s) after successful ingestion (default: `false`).
  - `--reindex`: Reindex the search engine after ingestion (default: `true`).
  - `--json`: Output structured JSON report (`IngestReport`).
* **Backward Compatibility**:
  - If executed without arguments or with `--zip`, it continues to invoke the existing meeting processing pipeline in `inbox/`.

#### 3. ConnectRPC Service (`api/v1/graph.proto`)

The `GraphService` interface is expanded to support host path ingestion and configurable destination folders:

```protobuf
service GraphService {
  // Existing RPCs...
  rpc IngestPath(IngestPathRequest) returns (IngestPathResponse);
  rpc CaptureNote(CaptureNoteRequest) returns (CaptureNoteResponse);
}

message IngestPathRequest {
  string path = 1;
  string destination = 2; // Default: "inbox"
  bool recursive = 3;     // Default: true
  bool move = 4;          // Default: false
}

message IngestedItem {
  string source_path = 1;
  string rel_path = 2;
  string title = 3;
  int64 size_bytes = 4;
  string warning = 5;
}

message IngestPathResponse {
  repeated IngestedItem items = 1;
  int32 total_processed = 2;
  string warning = 3;
}
```

The existing `CaptureNoteRequest` message is extended with an optional `destination` field (defaulting to `"inbox"`).

#### 4. Model Context Protocol (MCP) Tool Suite (`internal/mcp/server.go`)

Two first-class MCP tools empower autonomous coding agents to ingest external context:
1. `ingest_note`:
   - Accepts `title`, `content` (Markdown), optional `destination` folder, `tags`, and `source_url`.
   - Persists note via `internal/ingest.Engine.IngestContent`, updates search index, and returns relative vault path.
2. `ingest_path`:
   - Accepts host filesystem `path`, optional `destination`, `recursive`, and `move` flags.
   - Ingests single files or complete directory hierarchies, returning an `IngestReport` JSON payload.

#### 5. Web Cockpit Ingestion (`QuickCaptureDialog.tsx`)

`QuickCaptureDialog` is enhanced with a multi-tab interface:
- **"Write Note" Tab**: Standard fast capture for manual text input into `inbox/`.
- **"Import Files / Host Path" Tab**:
  - Drag-and-drop zone with browser `<input type="file" multiple accept=".md,.markdown,.txt" />` support.
  - Direct host path input field for daemon-side filesystem ingestion.
  - Destination directory selector with default `"inbox"`.
  - Visual ingestion feedback listing processed notes with direct links to focus the newly ingested nodes in the galaxy graph.

#### 6. Terminal UI (TUI) Ingestion View (`internal/tui/ingest_view.go`)

A dedicated `"9: 📥 Ingest"` tab is added to the Bubble Tea TUI:
- **Left Pane**: Interactive directory tree using `bubbles/filepicker`, enabling intuitive traversal of host directories (`~`, `/tmp`, etc.).
- **Right Pane**: Content preview of the highlighted markdown file, target destination input, and quick-action keybindings (`[Enter] Ingest File`, `[d] Ingest Entire Directory`).
- **Bottom Pane**: Audit ledger of files ingested during the active session with status badges (`🟢 Ingested`, `🟡 Reindexed`).

## Consequences

### Positive

* **Universal Knowledge Ingestion**: Users and AI agents can bring notes, RFCs, and documentation trees into Daneel from any interface (CLI, TUI, Web, MCP) with zero friction.
* **Rock-Solid Security & Integrity**: Strict vault containment, symlink rejection, and non-destructive collision avoidance guarantee zero file corruption or unauthorized access.
* **Rich Metadata & Provenance**: Frontmatter is preserved and augmented with clear provenance (`ingested_at`, `source_path`), maintaining high-fidelity knowledge graphs.
* **Real-Time Responsiveness**: Instant SQLite FTS5 reindexing and reactive ConnectRPC event streaming ensure newly ingested items appear in search and graph visualizations immediately.
* **Seamless Backwards Compatibility**: Existing meeting ingestion workflows and `CaptureNote` integrations continue to operate without breaking changes.

### Negative / Trade-Offs

* **Host Filesystem Access Permissions**: Ingesting files across diverse host operating systems requires appropriate read permissions on external directories.
* **Move Semantics Failure Recovery**: Using `--move` requires careful transaction handling so that source files are removed only upon fully verified disk writes.
